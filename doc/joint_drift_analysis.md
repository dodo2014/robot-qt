## 零、结果（2026-09-18 真机验证）

用户将 J1 参数由 **`maxSpeed` 30 °/s / `maxAccel` 200 °/s²** 调为 **25 °/s / 80 °/s²**，连续运行约 **247 轮（≈4 h）**，**目测无偏移**。逐日日志实测的下发参数与运行量：

| 日志 | J1 实际下发 `acc`（折算 `maxAccel`） | 轮次（回安全位次数） | 观察结果 |
| :--- | :--- | ---: | :--- |
| `2026-09-15` | **200 °/s²**（370 次）/ 80 °/s²（152 次）/ 100 °/s²（107 次） | 151 | **观察到漂移**（TR-095） |
| **`2026-09-18`** | **80 °/s²（1333 次，唯一档位）** | **247** | **无可见漂移** |

**这是 TR-095 用例 8.30（「J1 `maxAccel` 下调佐证」）的实测结果，机理得到确认。** 参数改动落在提交 `4c95d14`（2026-09-16）。

**一处对 TR-095 机理的细化**：TR-095 把重点放在**速度**（输出 30 °/s = 电机 500 rpm，步进失步高发区），并建议「降速 ≤70%」。但本次实际生效的是**加速度降 60%**（200→80）配 **速度仅降 17%**（30→25）。物理上，巡航段的力矩需求只有摩擦与重力载荷，而**加减速斜坡段的力矩需求 = 转动惯量 × 角加速度**，量级高得多——**失步最可能发生在斜坡段而非巡航段，故加速度是比速度更有效的杠杆**。（两者同时改动，无法完全隔离；此判断属机理推断，见 §七 待确认 1。）

## 一、结论

1. **根因＝J1 开环步进失步**（TR-095 立论，本文 §零 实测确认）。**软件侧已排除**——不是推理，是实测：当日日志中 J1 的**下发目标只有 4 个固定值，1333 次下发零变化**（§四）。方案点位来自 `process.json` 常量 + 确定性逆解，软件不可能产生累积漂移。
2. **误差只会「累积」、不会「回落」**，这是开环步进 + **绝对脉冲定位**的固有性质，不是故障（§二）。**软件对物理偏差既不知情、也无纠正手段**，因为卡内位置寄存器是**指令计数器**而非反馈。
3. **有效杠杆是加速度**（§零）：斜坡段的力矩需求 = 转动惯量 × 角加速度，远高于巡航段；`maxAccel` 200→80 °/s² 后 247 轮无可见漂移。

**两条仍然成立的结论，与「已缓解」不矛盾**：

- **唯一能重新建立机械基准的动作是回零**，而循环生产**不在轮次间回零**（`SequenceWorker` 只有回零互斥门禁，无重回零逻辑）。所以**残余失步仍然会被静默累积**——「已缓解」不等于「已归零」（§六）。
- **降加速度是拿节拍换精度**。若后续要做节拍优化（`doc/implementation_roadmap.md` 的 P6），这两者会直接冲突；**`smoothTime` 是能同时保住两者的杠杆**（§五 M1、§八）。

## 二、根因机制：为什么开环绝对定位「只累积不回落」

### 2.1 卡内位置寄存器是指令值，不是反馈值

`BoPaiCard::GetPosition`（`src/HAL/motioncard/BoPaiCard.cpp:510-515`）返回 `lastStatus_[axisId].position`；该字段由 `RefreshStatus`（`:164-198`）填充，取值处 `:190-192` 与源码注释：

```cpp
// 状态回读：直接回读卡内位置寄存器（脉冲），与 IMotionCard「脉冲单位」契约一致；
// 物理换算统一由 HardwareManager/AxisConverter 完成。
s.position = static_cast<double>(impl_->sysStatus.lAxisPrfPos[axisId]);
```

`lAxisPrfPos` 是 **轮廓位置 (Profile Position)**，即梯形速度规划器的**输出值**——卡认为自己下发了多少脉冲。开环步进无编码器，**失步对它是不可见的**。

**推论（本节最重要）**：只要卡不报故障，`PrfPos` **恒等于最后一次下发的目标**。因此：

- **UI 上的 J1 角度每轮必然一模一样**，无论物理上偏了多少；
- 由此可知：**「UI 数值不变 ⇒ 软件无罪」这个推理不成立**——它是必然结果，不构成证据。详见 §五 E1。

### 2.2 为什么偏差不会被自动纠正

```
第 1 轮：卡内 PrfPos=0 → 下发绝对目标 711100 Pulse（=100°）
        → 卡发出 711100 个脉冲 → 物理实际只走了 711030（失步 70）
        → 物理位置短 70 Pulse，但 PrfPos 已记到 711100
第 2 轮：下发同一绝对目标 711100 → 卡认为「已在位」→ 发出 0 个脉冲
        → 物理短少的 70 Pulse 原样保留，且后续每次移动继续叠加新的失步
```

`DispatchPointMove`（`src/Logic/SequenceWorker.cpp:48-68`）的「已在位则跳过」逻辑正是这个比较：

```cpp
constexpr double kInPositionEps = 0.01;   // 0.01 mm（Z）/ 0.01°（J1/J2/R）
if (std::fabs(c.target - hw.GetPosition(c.axis)) <= kInPositionEps
    && hw.IsWithinSoftLimits(c.axis, c.target)) {
    SPDLOG_INFO("[SequenceWorker] skip axis {} (in position)", c.name);
    continue;
}
```

两边都是**软件量**（新目标 vs 卡内 PrfPos），所以这段逻辑**既不制造也不掩盖**物理漂移；它的实际作用是**让软件永远不会去「补」那 70 Pulse**。

### 2.3 分辨力量级

J1 的 `PulsePerUnit`（`BoPaiCard.cpp:118-139`）：

```
encoderResolution 25600 × microSteps 1 = 25600 steps/rev（电机）
÷ gearRatio 0.01（1:100 谐波，输出端转数/电机转数） = 2 560 000 steps/输出端转
÷ 360 = 7111.1 Pulse/°
```

- **1 Pulse ≈ 0.000141°**
- `kInPositionEps = 0.01°` ≈ **71 Pulse** —— 即：**失步量小于 71 Pulse 时，软件连"该补一下"都判断不出来**

| # | 外部模型的说法 | 事实 | 影响 |
| :--- | :--- | :--- | :--- |
| **E1** | 「【情况 A】UI 数字和第 1 轮一模一样 ⇒ **软件 100% 无罪**」 | **推理无效**。`lAxisPrfPos` 是指令计数器（§2.1），**UI 每轮必然一模一样**，与物理是否漂移无关。该测试**无鉴别力** | 会让排查者**过早排除软件**，或反过来在情况 B 时误判方向 |

### 6.2 仍建议执行（按价值排序）

**D6 —— 量化漂移（把「目测」变成数字）**
本问题两次判定（发现与缓解）都是**目测级**。建议在方案第一个动作的初始位置做一次**带基准的定量测量**：断电后在 J1 臂端与固定参考物之间做标记（或架百分表），记录 250 轮前后的读数差。
- 产出形如「**0.0X mm / 250 轮**」的数字。这是唯一能回答「残余失步是否已被压到 0」的方法。
- 若读数差为 0（在测量分辨力内）→ 该加速度档可长期使用，`doc/implementation_roadmap.md` 的 P6 节拍优化可以放心推进。
- 若读数差非 0 → 仍有残余失步，且**不会被自动纠正**（§2.2），需按 D7 或 D8 处置。

**D7 —— 划线法（一次性排除机械打滑）**
断电，在 J1 电机出轴、联轴器、减速机输入轴上画一条连续直线 → 上电跑一轮长循环 → 断电看线是否错位。
- **说明**：D5 的成功**倾向**指向失步（机械打滑通常表现为更大、更无规律的偏差），但**不能严格排除**——联轴器打滑同样会随力矩尖峰加剧，而力矩尖峰正比于角加速度。故若要让结论无保留，仍需这一次划线。
- **错位** → 机械打滑，属紧固问题（螺丝胶 / 铣平面）；**不错位** → 失步确认。

**D8 —— 加速度边界扫描（要节拍就做这个）**
`maxAccel` 从 80 °/s² 起**逐步上调**（如 100 / 120 / 150），每档配 D6 的定量测量，找出**无可见漂移的最高值**。
- 直接收益：把「降加速度换来的精度」在可接受范围内**买回一部分节拍**。
- 与 `doc/implementation_roadmap.md` 的 **P6（动作树并发）**直接相关——两者都在争节拍，应合并考虑而非各自调参。

### 6.4 失步量级估算（推断，与 §零 结果一致）

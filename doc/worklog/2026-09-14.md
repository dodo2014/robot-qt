### 3.2 三项关键设计取舍

1. **循环外壳放会话内，而非启动层**。若在 `RunSequence`/`StartExecution` 层做循环，取消、暂停门禁、故障锁存、会话结束信号都要各自长一套循环感知逻辑；放进 `ExecuteActions` 后，这些全部沿用原有单点。
2. **`errorOccurred` 单点化（D17 方案 A）**。`ExecuteAction` 子树原有 **8 处** `emit errorOccurred` 改为写 `impl_->lastError`（值语义，仅 worker 线程读写），emit 收敛到 **2 处会话级出口**（`ExecuteOnce` 失败分支 / `StartSingleExecution` 兜底），两处均用 `lastError.isEmpty() ? action.name : lastError`。**`ExecuteActionWithRetry` 自身不 emit**——耗尽后把原因留给上层，否则会与 `ExecuteOnce` 的失败分支重复发两次。**顺带修掉一处既有瑕疵**：原先动作失败会发**两条** `errorOccurred`（内部具体原因 + 外层 `action.name`），`AutoRunPage::OnError` 里 `m_lastError` 被后者覆盖 → 清报警提示丢失具体原因。
3. **`DispatchPointMove` 的 ε 跳过（D19）**。新增匿名 namespace 函数统一四轴下发（先舵机 J2/R 再卡轴 J1/Z），**目标与读回当前值之差 ≤ 0.01 的轴跳过下发**并写 `SPDLOG_INFO skip axis X (in position)`。跳过前**仍过 `IsWithinSoftLimits`**——不旁路软限位硬拦截，越界照走 `MoveAbs` 的完整拒绝路径；`reissue` 复用同函数，故恢复瞬间不把已在位轴重下发。**正面副作用**：每点 4 次 `InMainThread` 合为 1 次；同高度平移不再白等 200ms/轴。

### 3.3 命名偏差（以台账为准）

`Impl` 成员定名为 **`loopCfg`** 而非方案文档写的 `loop`——`Impl::WaitForCancelOrTime` / `WaitForStep` 内已有局部 `QEventLoop loop`，同名触发 **C4458**（声明隐藏类成员）。选择改己方命名，**不动既有等待循环**（那是精细调过的暂停感知代码）。已回写方案文档与 `TEST_RECORD.md`。

## 四、关键认知沉淀（当日新增）

1. **「设计上应该没问题」与「代码保证成立」之间通常差一个 `grep`**。用户要求确认「回安全位严格先抬 Z 到位再水平移动」时，结构层面确实成立（点粒度串行：`ExecuteMove` 逐点循环 + 每点 `WaitForAxes` 阻塞至全部参与轴到位）；但读代码才发现两点限制：① **到位判定是时间估算**而非位置反馈（`MarkAxisBusy` 写 `距离/速度×1000 + 200`，开环步进无编码器，全项目 `MoveAbs` 共用）；② 点 1 会把 J1/J2/R **重下发为读回当前值**，而舵机 `ReadAngle()` 上报角度在减速停后可能与指令有微差 δ → 存在真实的**低位水平微动**窗口。D19 的 ε 跳过即针对 ②。
2. **设计稿里的代码片段引用不存在的符号，是最隐蔽的一类过期**。`auto_run_loop_production.md` 引用的 `ExecuteActionOnce(act, idx)`（真实为 `ExecuteAction(action, index)`）与 `WaitWithGate(ms)`（不存在）**读起来完全自洽**——名字都很"像"，只有全仓库 `grep` 才能证伪。同类还有「复用 Delay 类等待的暂停通道」的说法：`ExecuteDelay` 的暂停感知是自写的 `for(;;)+PauseGate()` 循环，而 `WaitForCancelOrTime` **只处理 cancel、不处理 pause**。**评审设计稿必须逐符号 grep，不能只读逻辑。**
3. **AI 面向的规范文档，价值集中在「可判定的具体规则」**，而非角色扮演与威慑措辞。v1 的「你必须先读，否则我中断对话」属软约束且带流程税（该条从未被执行过，只会多一次往返）；v2 改为「文档内自带适用范围声明 + 输出自检清单」，让规则可被逐条核对。
4. **术语表的边际价值 = 「看起来对但其实错」的词**。`支付载荷`「方式点」这类荒谬反例模型本来就不会产出，属低收益行；真正值钱的是 `TCP`（工具中心点 ≠ 传输控制协议）、`encoderResolution`（本项目开环步进无编码器，实为驱动器每转脉冲数）、`Home`（三义）、`Trap`（梯形速度规划）这类**多义/名不副实**条目。
5. **软约束要靠机制补硬**。AGENTS.md 全文会自动注入，但 `doc/` 下的正文不会——助手必须主动 Read 才知其内容，**读不读取决于自觉，且与任务类型相关**（改代码大概率读，看日志可能跳过，而恰恰那时也需要术语规范）。补法：走 SessionStart hook 注入（本次采用，成本 1 行）。

9. **环境事实（对后续会话有用）**：本机工具链读 UTF-8 中文有**偶发乱码显示**（`ConfigManager.h` 的 BOM + 内容组合会触发），**判断中文内容务必用 Python 显式 `encoding='utf-8'` 读**，别依赖终端 `cat`/`cut`/`grep` 的显示。本次即因此一度误判为「显示问题」，字节级核对后才确认是真损坏；另 `cut -c` 按字节切，看 UTF-8 中文必乱码。
10. **沙箱编译的可用路径**：PowerShell 工具**跑不了 native exe 的管道/重定向**（`| Select-Object` 报 `CantActivateDocumentInPipeline`；`*>` 不报错但**输出全丢、日志 0 字节、`$LASTEXITCODE` 空**，极易误判为成功）；`build_debug.bat` 因 vcvars64 依赖 `reg.exe` 被拦而静默无输出退出；`Start-Process` 同样被拦。**可用路径 = 手工构造 INCLUDE/LIB/PATH + Bash 工具跑 Git Bash 调 ninja**。已固化进 `doc/compile_guide.md` §3.3/§3.4。
11. **用 `grep` 核验结构化 JSON（NDJSON）会产生假阴性**。本次查 `.history/pending.ndjson` 的压缩 marker 时，grep 返回「最新 marker = 09-08」，与 `state.json` 记的 09-11 矛盾，一度被当成数据不一致。改用 Python `json.loads` 逐行解析后发现：最新 marker **确实是 2026-09-11T09:03:02（第 33 行）**，只是 marker 记录用 `compactedAt` 键而非 `ts`、且键序与普通提问记录不同，正则匹配不到。**教训：核验结构化数据的字段值，必须走解析器；grep 只适合「某字符串是否存在」这类布尔判断。**
12. **同一次操作里，终端显示乱码与数据真实损坏必须分开判定**。本次 `head | cut` 显示 `pending.ndjson` 中文为 `[瀹炴柦]`（与 `ConfigManager.h` 的双重编码外观**完全一致**），但 Python 严格 UTF-8 解码通过、内容为正确的 `[实施]`——即纯显示假象。而 `ConfigManager.h` 两行在同样手段下解码后仍是乱码，才是真损坏。**同一个「乱码」外观，两种截然不同的结论，只能靠「严格解码是否通过 + 还原后是否为合法中文」两步判定。**

拍照标识（captureTag）是什么
动作级的业务标签，一处填写、三处使用：
① 文件名 — RGB_A02_20261026_103058_003.png
② 通知 — captureReady / captureFailed 载荷里的 tag
③ sidecar — 同名字段
用途是分类归因：第三方拿到一堆图后，靠它判断「这张拍的是哪个部位 / 哪类缺陷」，而不是靠文件名顺序或时间猜。
校验：必填；同方案内不允许重复（含分组内子动作，全树扫描）；字符集 [A-Za-z0-9_-]；上限 32 字符。
⚠ 字符集为什么收紧：它要进文件名，中文 / 空格 / 冒号在 Windows 与 Linux 两端行为不一致。需要中文描述时，由第三方侧维护「编码 → 中文」映射表。
⚠ 仍与检测项 items[].key 不是一回事（那个标识「测的是什么量」，见 inspection_result_panel_plan.md:62）。
来源 §1.2 裁定 3 + 2026-10-26 裁定（合并「图片标识」）。
已与「图片标识」合并为一个字段：原设计里两者语义相同（都是「这张图是什么」），只是去向不同（一个进文件名、一个进通知），分开会导致两套唯一性校验、且值不一致时第三方归因断裂。合并后一处填写、三处一致。
副产品：唯一性约束只剩一条，同时满足「通知可归因」与「文件名不撞名」—— 原来靠「图片标识唯一」补的「新文件名丢了 nodeId」的洞，现在由 tag 唯一性天然覆盖（同轮同秒同 tag 只可能是同一动作触发两次，靠序号区分）。
代价：字符集必须收紧到 [A-Za-z0-9_-]（因为要进文件名），中文与空格不可用。
⚠ 唯一性校验必须全树扫描（一级节点 + 分组子节点）—— 拍照可以放进分组，只扫一级会漏。

关闭后的行为（fail-open）
失败时只记 SPDLOG_WARN + 发 captureFailed{nodeId, cycleIndex, tag, reason}，流程继续下一节点。
  1. 必须发 captureFailed——否则第三方分不清「这一轮还没拍」与「拍了但失败被跳过」，图片数量对不上却无法归因。
  2. 不得复用 errorOccurred——全库 7 处 emit errorOccurred 全部伴随会话中止，复用即误报。须守住「errorOccurred ⟺ 会话中止」不变量。
  3. 必须有兜底——连续失败 3 次或相机流本身掉线，仍判失败中止；否则相机被拔掉后整晚会空转。
  4. 只豁免拍照动作自身，不影响其它动作类型的失败语义。
来源 §1.4 裁定 1 / §5.6。默认 fail-closed。文案须与识别动作区分：识别失败是「视觉未检出目标」（业务语义，图是好的），拍照失败是「取帧失败 / 帧无效 / 落盘失败」（故障语义）。
三条硬约束已移入「?」气泡（2026-10-26 裁定 3），界面不再铺开。

两条通道，可单选、可同选
路径引用 captureReady：只发路径 + 元信息（fileName / filePath / depthFile / width / height / timestamp），第三方自己去读文件。
直接推送 captureData：一帧 JSON 描述 + 紧接一帧二进制图，第三方不用碰磁盘。
怎么选：同机部署（第三方服务与本软件在同一台机器）→ 路径引用足够，省掉一次完整图像传输；跨机且第三方读不到本机磁盘（无共享盘 / 无权限）→ 必须直接推送。两者同开 = 既能立刻用内存图，又能事后回查原文件。
⚠ 两条通道都只等本地落盘完成，不等网络 ACK（§5 约束 1）；顺序固定：写图 → rename → 写 sidecar → 发通知（§5 约束 2）。
